# Spendguard

**A neural circuit breaker for hot wallets and AI-agent wallets.** A small neural network runs
*inside* a Reactive contract on Reactive Lasna. It scores every spend a guarded wallet makes on
Base Sepolia, and when the score crosses a threshold it sends a callback that freezes the wallet.
Every inference is a Lasna transaction; the weights are compiled into the contract.

Built for the *Reactive Meets AI* track of the Reactive Omni Buildathon. Testnet only.

> Status: live on testnet (2026-11-09). In the recorded run the network flagged the attacker's
> second near-cap spend (score 564 ≥ 472), the freeze landed on Base **2 seconds** later, and the
> next spend was refused. Every on-chain score matches the Python reference exactly
> ([replay](evidence/live-replay-run2.txt)).

## Problem

An AI agent that pays for things needs a hot key. If that key or the agent is compromised, the
attacker can drain the wallet one valid transaction at a time; a per-call cap only slows that down.
Owners want something that watches *every* spend, notices when the pattern stops looking like
their agent, and stops the wallet without waiting for a human or an off-chain bot.

## How it works

```
 Base Sepolia                               Reactive Lasna
 ┌────────────────────────────┐             ┌──────────────────────────────────────────┐
 │ GuardedWallet              │  Spend log  │ SpendguardReactive.react()               │
 │  agent ── spend(to, amt) ──┼────────────▶│  1. update rolling state (decayed sums)  │
 │  (per-call cap, !frozen)   │             │  2. build 9 integer features             │
 │                            │             │  3. MLP 9 → 12 ReLU → 1 (fixed point)    │
 │                            │             │  4. emit Scored(nonce, score, features)  │
 │  freeze(rc, epoch, nonce,  │◀────────────┼─ 5. score ≥ threshold → requestCallback  │
 │         score)             │  callback   │                                          │
 │  owner ── unfreeze() ──────┼─ Unfrozen ─▶│  new epoch → reset rolling state         │
 └────────────────────────────┘             └──────────────────────────────────────────┘
```

- **`src/GuardedWallet.sol`** (Base Sepolia, `AbstractCallback`). Holds a demo ERC20. The `agent`
  (hot key) calls `spend(to, amount)`, which requires `!frozen`, `amount <= cap`, the rolling
  window limits (default: 3 × cap and 20 spends per hour, owner-settable with `setWindow`) and no
  outstanding callback-fee debt, and emits `Spend(nonce, to, amount, balanceBefore, timestamp, epoch)`.
  The window bounds what a compromised agent can move before a freeze can land (for example many
  spends in one block); the debt check makes the wallet stop rather than run unguarded when it could
  not receive a freeze. `freeze(...)` is accepted only from
  the Reactive callback proxy carrying this specific reactive contract's address
  (`onlyServiceProvider` + `onlyCallbackSender`), only for the current epoch, and it only sets
  `frozen`. **No callback moves tokens.** The `owner` (cold key) can `unfreeze()` (starts a new
  epoch, which makes queued freeze callbacks stale), `setAgent`, `setCap`, `withdraw` (also while
  frozen) and `withdrawNative`.
- **`src/SpendguardReactive.sol`** (Lasna, `AbstractReactive`). Subscribes to the wallet's `Spend`
  and `Unfrozen` logs. For each new `Spend` (replay key = chainId + txHash + logIndex) it builds the
  features, calls `SpendguardModel.score`, emits `Scored` for every spend and, on the first flagged
  spend of an epoch, requests `freeze`. If the wallet is still spending `retryAfter` seconds (event
  time) after a request, the request is sent again. `scoreFeatures(x)` lets anyone re-run the
  deployed network with an `eth_call`; `modelHash()` returns the SHA-256 of the quantized weights.
- **`src/SpendguardModel.sol`** is generated by `model/train.py`: constants, the threshold, and an
  unrolled integer MLP. It is not edited by hand.

Why Reactive: the wallet cannot watch its own history cheaply or call itself later, and an
off-chain watcher would be one more key and server to trust. Here the scoring runs as a Reactive
transaction triggered by the wallet's own log, and the only power it has is the narrow freeze
callback. A keeper bot could implement the same policy; Reactive is what makes it run with no
operator, and makes every inference a public transaction.

## Features

All features are integers computed in `react()` from the `Spend` log and the contract's rolling
state. Time comes from the log's `timestamp` field (Base `block.timestamp`), because a Reactive
`LogRecord` carries no source timestamp. Decay is `v · 2^(−dt/h)`: whole half-lives as bit shifts,
the remainder as a straight chord. `log2fx(n) = 16·floor(log2 n) + next 4 mantissa bits`.

| # | Name | Definition |
|---|---|---|
| 0 | `frac` | `log2fx(amount · 2^16 / balanceBefore + 1)` — size relative to what is left |
| 1 | `gap` | `log2fx(seconds since previous spend + 1)`; first spend of an epoch uses 2^17 s |
| 2 | `burst` | spend count decayed with a 120 s half-life (one spend = 256) |
| 3 | `rush` | sum of `amount/balanceBefore` decayed with a 120 s half-life (100 % = 4096) |
| 4 | `flow` | the same sum with a 1800 s half-life |
| 5 | `recipAge` | `log2fx(seconds since recipient was first paid + 2)`; 0 if never paid |
| 6 | `fresh` | count of spends to *fresh* recipients (never paid, or first paid < 600 s ago), 600 s half-life |
| 7 | `freshFlow` | outflow fraction sent to fresh recipients, 600 s half-life |
| 8 | `size` | `log2fx(amount + 1) − log2fx(typical + 1)`, clamped to ±8 doublings; `typical` is an EMA (1/8) of past amounts |

Rolling state (`burst`, `rush`, `flow`, `fresh`, `freshFlow` and the gap clock) resets on every new epoch. The profile (`typical`, first-paid
times) survives epochs, and **only spends scored below the threshold are learned**: a recipient first
paid in a flagged spend does not become "known" after an unfreeze. A recipient that already received
an unflagged spend (like X at spend 6 in the demo) has been learned.

## Model

- MLP **9 → 12 ReLU → 1**, 133 integer parameters. Layer-1 weights are scaled by 2^20, layer-2 by
  2^14; the output is the logit × 256. Input standardization is folded into layer 1 before rounding.
  Hidden size was picked on validation from {8, 12, 16}.
- Threshold **472** (logit 1.84): the lowest score at which at most 1 % of *validation* normal
  sequences (60 spends each) would ever be frozen.
- Trained with weighted logistic loss (numpy, Adam). Early attacker spends get more weight (halves
  every 3 spends into an attack), and three hard-negative rounds up-weight the highest-scoring
  normal spend of each sequence, because one high score anywhere in a normal sequence is what
  causes a false freeze.
- Python reference (`model/spendguard_ref.py`) is integer-exact: it mirrors the Solidity feature
  code and inference operation by operation. The Foundry tests check that the contract reproduces
  every vector in `test/vectors.json` exactly.

### Data: synthetic

**There is no public labelled dataset of compromised agent-wallet spends, so the data is
synthetic** (`model/generate.py`, fixed seed). Normal agents pay a small pool of regular
recipients at irregular intervals (median gap 50–1000 s), sometimes add a new vendor, sometimes
batch a few quick payments, occasionally make a larger payment, and are topped up by the owner.
Attack patterns start after a normal prefix: **burst** (near-cap spends every 2–15 s to new
addresses), **sweep** (1–4 large spends), **drip** (spends just under the cap at the agent's own
pace), **spray** (normal-sized spends to a different new address every 5–60 s) and **mimic**
(normal amounts at normal pace to one new address). The numbers below show that the mechanism works
on these patterns. They are not a claim about real-world accuracy.

### Results (held-out test set, from [model/REPORT.md](model/REPORT.md))

Both methods get the same false-freeze budget on validation; the baseline is the best
single-feature threshold rule over all 9 features, both directions.

| | Neural net | Best single rule `freshFlow >= 951` |
|---|---|---|
| Normal sequences frozen (false freeze) | 0.9 % | 0.7 % |
| Attacks detected | **57.1 %** | 39.8 % |
| Mean share of balance lost per attack (no guard: 48.3 %) | **26.3 %** | 28.3 % |
| Per-spend ROC AUC | 0.862 | 0.741 |

| Pattern | NN detected | Rule detected | NN lost | Rule lost | No guard lost |
|---|---|---|---|---|---|
| burst | 100.0 % | 98.4 % | 19.8 % | 27.9 % | 85.7 % |
| sweep | 29.1 % | 29.9 % | 13.7 % | 14.1 % | 18.7 % |
| drip | 70.1 % | 40.2 % | 61.7 % | 61.3 % | 90.7 % |
| spray | 80.5 % | 32.3 % | 11.3 % | 14.2 % | 21.3 % |
| mimic | 8.2 % | 1.5 % | 30.1 % | 28.8 % | 32.3 % |

"Lost" assumes the freeze lands 10 s after the flagged spend (spends inside that window go
through) and attack spends spaced 2–15 s apart. An attacker who sends many spends in the same block
is not slowed by the network at all; there the wallet's window limit is what bounds the loss
(3 × cap per hour by default). At budgets of 0.5 %, 2 % and 5 % the network also detects more attacks than the best
single rule (table in the report).

Caveat on the test set: thresholds and architecture were chosen on validation only, but held-out
test numbers were printed during hyper-parameter sweeps, so the test set is not perfectly untouched.

What the network adds, honestly: it detects more attacks than any single feature at the same
false-freeze budget, mainly drip and spray, which need several weak signals together. It barely
changes the outcome for sweeps (a few large spends finish before any guard can react; the cap is
what limits them) and it does not catch `mimic`, which looks like an agent adding a new vendor.
For drip, it detects more often but late, so the loss is about the same as the rule's. The
balance-loss gain overall is modest (26.3 % vs 28.3 %); the clearest gain is on bursts, where it
freezes earlier.

## Reproduce and verify

```sh
python tools/bootstrap.py                 # pinned reactive-lib-omni + forge-std into lib/ (gitignored)
cd model
uv venv .venv && uv pip install -r requirements.txt   # numpy only, into ./.venv
.venv/bin/python generate.py              # writes data/summary.json (optional)
.venv/bin/python train.py                 # weights.json, REPORT.md, ../src/SpendguardModel.sol, ../test/vectors.json
cd ..
forge test -vv                            # Windows: ./tools/test.ps1
python tools/mutation_check.py            # breaks 3 properties, requires failures, restores
```

On Windows use `.venv\Scripts\python.exe`. Training is deterministic for a given numpy build
(re-running here reproduced identical `weights.json`, `SpendguardModel.sol` and `vectors.json`).
Other numpy/BLAS builds may differ in the last bits and then produce different weights; the
committed `weights.json` is the artifact the contract is generated from.

**Check the live system yourself.** `model/replay.py` (standard library only) recomputes every
score from the wallet's `Spend` logs and compares it with the reactive contract's `Scored` logs:

```sh
cast logs --json --rpc-url https://sepolia.base.org --from-block <b> --address <WALLET> \
  "Spend(uint256 indexed,address indexed,uint256,uint256,uint256,uint256)" > spend.json
cast logs --json --rpc-url https://lasna-rpc.rnk.dev/ --from-block <b> --address <REACTIVE> \
  "Scored(uint256 indexed,uint256 indexed,int256,int256[9],bool)" > scored.json
python model/replay.py --spend-logs spend.json --scored-logs scored.json
```

`cast call <REACTIVE> "scoreFeatures(int256[9])(int256)" "[...]" --rpc-url https://lasna-rpc.rnk.dev/`
runs the deployed network on any feature vector.

## Tests

`forge test -vv` (Foundry 1.8.6, Solidity 0.8.30, via-IR): **28 tests, all passing** — 17 in
`SpendguardTest` (one is a 256-run fuzz test), 9 in `test/Review.t.sol`, 1 deploy-script test, and an
invariant suite with 3 invariants (128 runs × 64 calls, 0 handler reverts). Raw output:
[test-results/restored-pass.txt](test-results/restored-pass.txt).

- Pre-deployment review (`test/Review.t.sol`): a same-block drain is now stopped by the window
  limit after 3 × cap; a wallet billed into debt by foreign callbacks stops spending instead of
  running unguarded, while the owner can still withdraw; plus documented edge cases (recipient
  learning, replay keyed by log rather than nonce, extreme amounts). Removing the window check makes
  both window tests fail ([test-results/mutation-window.txt](test-results/mutation-window.txt)).

- Inference parity: 244 feature vectors (240 held-out samples + 4 extremes) → exact score.
- Sequence parity: 8 sequences (demo, normal-only demo, one held-out sequence per pattern) →
  exact features, score, flag and index of the first freeze request.
- End-to-end demo through the real wallet: no request before spend 7, request at spend 7,
  callback delivered, next spend reverts `frozen`, balance matches.
- Normal sequences never request a freeze; spends revert while frozen and the owner can still
  withdraw; `unfreeze` advances the epoch, the queued (stale) freeze is ignored, the `Unfrozen` log
  resets rolling state; a `Spend` with a newer epoch also resets it; late spends from an old epoch
  are ignored; only the proxy carrying this reactive address can freeze (plus fuzz); `react()` only
  from the system contract, foreign origins ignored; replayed logs are no-ops; cap and agent
  enforced; retry when the wallet keeps spending; callback fees cannot touch token principal.
- Invariants: a frozen wallet never loses tokens through `spend`; freeze callbacks never move funds;
  wallet balance + spent = initial funding.
- Deploy script: all five stages run offline with faked chain ids; reruns are idempotent;
  non-target chains and wrong-chain stages revert.
- Mutation check ([test-results/MUTATION.md](test-results/MUTATION.md)): removing the `frozen`
  check fails the invariant; changing the model's output shift fails inference parity; changing
  the `gap` feature fails sequence parity. Sources are restored and the suite passes again.

**Gas.** `react()` measured locally with a no-op system contract (`test_ReactGas`):
104k–128k per spend, 175k for the first spend (cold storage). The real system contract's cost for
`requestCallbackV_1_0` is not included; `forge test --gas-report` numbers
([test-results/gas-report.txt](test-results/gas-report.txt)) include the recording mock's storage
writes and are higher. `scoreFeatures` (inference only) is about 18k gas. The `freeze` callback uses
at most 48k gas on the wallet; the callback gas limit defaults to 500,000 (see the first live run below for why 200,000 was not enough).

The system contract and callback proxy are local test doubles: these tests do not prove
subscription delivery, callback signing, fee billing or latency on the live networks.

## Deploy (testnet)

Use a dedicated test wallet. Put `PRIVATE_KEY` (owner) and, for spends, `AGENT_PRIVATE_KEY` in the
process environment from a secret store; never on the command line or in files. `OWNER` must match
`PRIVATE_KEY`. See [.env.example](.env.example) for the other variables. `tools/deploy.ps1` sets
`STEP` and `EXPECTED_CHAIN_ID` from `config/networks.json`; without `-Broadcast` it only simulates.

| Variable | Stage | Meaning |
|---|---|---|
| `OWNER`, `PRIVATE_KEY` | all | owner address and key |
| `TOKEN_SUPPLY_WEI` | token | demo sgUSD supply minted to OWNER |
| `REACTIVE_FUND_WEI` | reactive | lREACT sent to the reactive contract for reactive-tx fees |
| `THRESHOLD`, `CALLBACK_GAS`, `RETRY_SECONDS` | reactive | optional; default model threshold, 500000, 60 |
| `TOKEN`, `REACTIVE`, `AGENT`, `CAP_WEI`, `CALLBACK_FUND_WEI`, `FUND_WEI` | wallet | wallet wiring; ETH for callback fees; tokens to deposit |
| `REACTIVE`, `WALLET` | link | subscribe the reactive contract to the wallet |
| `WALLET` | unfreeze | owner lifts a freeze |

```powershell
./tools/deploy.ps1 -Step token    -Network base  -Broadcast; $env:TOKEN    = '<TestToken>'
./tools/deploy.ps1 -Step reactive -Network lasna -Broadcast; $env:REACTIVE = '<SpendguardReactive>'
./tools/deploy.ps1 -Step wallet   -Network base  -Broadcast; $env:WALLET   = '<GuardedWallet>'
./tools/deploy.ps1 -Step link     -Network lasna -Broadcast
```

The reactive contract is deployed before the wallet because the wallet pins its address as the
only callback sender; `link` then subscribes. Setting an existing address variable makes a stage
skip creation. Each demo spend:

```powershell
$env:TO = '<recipient>'; $env:AMOUNT_WEI = '4000000000000000000'
forge script script/Spend.s.sol:Spend --rpc-url https://sepolia.base.org --broadcast
```

## Running cost

Every spend from the guarded wallet is one reactive transaction on Lasna (~104k–175k gas of
contract execution locally, plus Reactive's own overhead) and every freeze is one callback
transaction on Base Sepolia, paid from the wallet's native ETH balance. Measured on Lasna: a
`react()` that scores a spend uses about 177k–214k gas and is billed about 0.018 lREACT at the testnet's
100 gwei (run 2: about 0.18 lREACT for linking, eight spends and the unfreeze). Read the live fee parameters and debts
with `cast call 0x8888888888888888888888888888888888888888 "debt(address)(uint256)" <REACTIVE>` on
Lasna and `cast call 0x476F44b11F5C942c58f4c8E3d0300E5710743585 "debt(address)(uint256)" <WALLET>` on
Base Sepolia. A positive debt stops delivery, so keep both contracts funded. Per Reactive's
documentation, a callback is billed to the receiving contract even if it reverts, and any reactive
contract can address callbacks to any callback contract, so a third party can spend the wallet's
fee balance; that is why `spend` refuses to run while the wallet is in debt. To recover, pay the
debt through the proxy's or system contract's `depositTo(address)` (a plain transfer only raises
the balance). `SpendguardReactive.withdraw` returns unused lREACT to the owner. For a production
wallet, the per-spend cost would need to be weighed against the value it protects.

## Limits

- **Synthetic data.** The model shows the mechanism; its accuracy on real agent wallets is unknown.
- **After the fact.** Spendguard scores a spend after it happened. Spends made before the freeze
  lands (Reactive delivery plus callback latency) go through; the per-call cap and the window limit
  bound how much that can be.
- **Replay key.** Spends are de-duplicated by (txHash, logIndex), not by wallet nonce; a re-org that
  re-includes a spend in a different transaction would be scored twice.
- **Freeze is all it can do.** The callback cannot move funds or change the cap; recovery is the
  owner's `unfreeze`/`withdraw`. A false freeze stops the agent until the owner acts.
- **Evasion.** An attacker who knows the features can spend slowly, in normal amounts, to one
  address (`mimic`); the model rarely catches that.
- **Fresh deployment.** The profile starts empty, so the first spends to each recipient look new.
- **One wallet per reactive contract**, one demo ERC20 with no fees or hooks. Testnets only. No UI.
- **Donations lower scores.** Tokens sent into the wallet raise `balanceBefore`, which lowers the
  size-relative features.
- **Liveness assumptions.** Delivery depends on the Reactive Network and funded fee balances. If the
  `Unfrozen` log is missed, the next `Spend` (which carries the epoch) resynchronises the state.
- Self-reviewed and AI-assisted; not an independent security audit.
